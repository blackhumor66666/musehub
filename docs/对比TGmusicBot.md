# 与 TGmusicBot 的关系说明

## 为什么是"重写"而不是"逆向"

原仓库 [huanhq99/TGmusicBot](https://github.com/huanhq99/TGmusicBot) 里**没有源码**——
README 明确写着"源码通过 Docker Hub 镜像分发", 仓库里只有文档、compose 文件和 CHANGELOG。

对分发镜像做反编译属于对作者作品的不尊重, 也有法律风险; 而且从工程角度完全不必要:
它对外暴露的**行为契约**(支持哪些平台、什么交互流程、什么环境变量)在 README 里写得
非常清楚, 足以做一份行为兼容的干净实现(clean-room reimplementation)。

所以 MuseHub 是: **参考其功能清单与接口形态, 从零重写**, 不包含其任何代码或二进制。
原项目 MIT 协议, 这种做法完全合规。

## 功能对照

| 能力 | TGmusicBot | MuseHub | 说明 |
|---|---|:-:|---|
| 网易云/QQ 歌单同步 | ✅ | ✅ | 同样支持链接识别、订阅、定时同步 |
| Spotify | ✅ | ❌ | 你没有提, 需要时加一个 provider 即可(约 200 行) |
| 无损/Hi-Res 音质 | ✅ | ✅ | 音质回退链机制 |
| 元数据/封面/歌词 | ✅ | ✅ | 额外修掉了"多艺人拼成一个目录名"的老毛病 |
| 文件整理器 | ✅ | ✅ | 规范化命名 + 与 Music Tag Web 配合 |
| Emby 集成 | ✅ | ❌→Navidrome | 你明确用 Navidrome, 做了原生适配(含歌单镜像) |
| TG 机器人 | ✅ 容易卡死 | ✅ 精简防卡死 | 见下文根因分析 |
| Web 管理面板 | ✅ | ✅ | 无构建步骤, 单文件 HTML |
| 扫码登录 | ✅ | ❌ 用 Cookie | 少一套扫码服务, Cookie 一次可用数月 |
| 国内中转代理 | ✅ | ❌ | 你本机在国内, 直连即可 |
| Redis 依赖 | ✅ 必需 | ❌ 不需要 | SQLite 就够了, 少一个容器 |
| 开放注册 | ✅ | ❌ | 自己用的工具不需要多用户 |

## 你反馈的"老是卡死"——根因与对策

| 根因(推断) | MuseHub 的对策 |
|---|---|
| 重活(同步/下载)直接跑在消息处理器里, TG API 超时拖死轮询循环 | 处理器只派后台线程, 毫秒级返回 |
| 无全局互斥, 重复触发导致任务堆积 | 同步引擎自带互斥锁, 重复触发直接跳过 |
| 依赖 Pyrogram 大文件上传, 事件循环复杂 | 不上传文件到 TG, 彻底移除该依赖 |
| Redis 连接抖动影响主流程 | 去掉 Redis, 全部 SQLite(WAL) |
| 无超时控制的外呼请求 | 所有外呼显式超时 + 指数退避 |
| offset 不落库, 重启后重复处理旧消息 | offset 落 SQLite |

## 有意省掉的东西

- **刮削** → Music Tag Web(你指定的分工)
- **播放** → Navidrome(你指定的分工)
- **扫码登录/用户系统/注册** → 单人工具不需要
- **Spotify** → 未提出需求, 架构上留了 `BaseProvider` 扩展点

> 推断声明: 上表"根因分析"部分基于原项目公开 README/依赖清单的合理推断
> (其源码未公开, 无法逐行核实), 不是逆向结论。
